## Chapter 3 — PFG: A Graph-Based Framework for Authorization Vulnerability Detection

### 3.1 Introduction and Core Insight

The core observation: authorization vulnerabilities are not about bad code patterns — they are about MISSING guards on execution paths. This structural nature makes them fundamentally different from injection/memory vulnerabilities and unsuitable for token-based or generic-graph approaches. Present the chapter's deliverable: a formal graph schema + hybrid neural/logical architecture.

### 3.2 Problem Formalization & Threat Model

#### Threat Model
- Attacker: authenticated user with valid credentials attempting privilege escalation or unauthorized object access
- Assets: REST API endpoints exposing object-level resources
- Trust boundary: authentication → authorization → data access chain
- Scope: Django/DRF and Spring Boot REST APIs

#### Taxonomy of Authorization Vulnerabilities (5 subtypes)
- MISSING_AUTH (CWE-306): no identity verification before data access
- MISSING_ROLE (CWE-862): no role/privilege elevation for sensitive operations
- IDOR (CWE-639): route parameter flows to data access without ownership check
- TENANT_ISOLATION_FAILURE: multi-tenant data reachable without tenant scoping
- OBJECT_LEVEL_PERMISSION_BYPASS: model-level permissions exist but not enforced

For each: formal definition, minimal code example, CWE + OWASP A01:2021 mapping.

#### Research Questions
- RQ1: Can a domain-specific graph representation effectively detect access control vulnerabilities in production web applications?
- RQ2: Does the framework provide interpretable, actionable results without post-hoc explanation techniques?
- RQ3: How does GNN-based detection compare with rule-based structural analysis and existing SAST tools?

### 3.3 Positioning Against Existing Paradigms

Make the argument ONCE, formally, here. Do not repeat elsewhere.

**Against NLP-based detection (CodeBERT, VulBERTa):**
Authorization is a cross-functional property spanning multiple files (urls.py → views.py → models.py). Token-based models operating on single-function windows cannot capture the inter-component relationship between an endpoint's URL configuration, its middleware chain, and its downstream data access. The security signal is structural, not lexical.

**Against generic Code Property Graphs (CPG/Joern):**
CPGs compose AST + CFG + PDG into graphs with thousands of nodes per function. For authorization detection, 99% of these nodes (syntax tokens, control flow branches, data dependencies) are irrelevant noise. The signal — "does a permission check exist between this entry point and this database query" — is buried. A domain-specific abstraction that models only the authorization-relevant components yields a 5–50 node graph where each node IS a meaningful architectural component.

**Our positioning:**
Purpose-built graph with interpretable features → no opaque embeddings needed. Structural path analysis → no post-hoc GNNExplainer needed. Both are eliminated by design, not compensated for after the fact.

### 3.4 The Program Flow Graph Formulation

#### Formal Graph Definition

$$G = (V, E, \tau_V, \tau_E, \phi_V, \phi_E)$$

where:
- $V$: set of nodes, $\tau_V: V \to \{\text{ENDPOINT}, \text{MIDDLEWARE}, \text{SERVICE}, \text{DATA\_ACCESS}\}$
- $E \subseteq V \times V$: directed edges, $\tau_E: E \to \{\text{CALL}, \text{IDENTIFIER\_FLOW}, \text{TENANT\_FLOW}\}$
- $\phi_V: V \to \mathbb{R}^{36}$: node feature vector
- $\phi_E: E \to \mathbb{R}^{3}$: edge feature vector (one-hot edge type)

Schema version 1.0, JSON-validated against pfg-1.0.json.

#### Node Types and Their Semantic Role

Explain WHAT each represents in the authorization decision chain:
- **ENDPOINT**: where the request enters (HTTP method, route, initial auth signals)
- **MIDDLEWARE**: what guards protect it (guard_type: authentication, role, ownership, tenant, object_permission)
- **SERVICE**: what logic processes it (business layer)
- **DATA_ACCESS**: what data is at stake (operation type, entity, ownership/tenant predicates)

A vulnerability exists when a path from ENDPOINT to DATA_ACCESS has insufficient MIDDLEWARE.

#### Feature Vector Justification (φ_V ∈ ℝ^36)

Rigorous justification of WHY each dimension exists. Table mapping:
- Feature index → property name → semantic meaning → which vulnerability subtype it detects

Feature categories:
- [0:4] node type identity
- [4:9] HTTP method (risk profile)
- [9] authentication requirement (MISSING_AUTH signal)
- [10:15] role requirement (MISSING_ROLE signal)
- [15] ownership check (IDOR signal)
- [16:19] guard type (path protection evidence)
- [19:23] operation type (damage potential)
- [23–35] authorization property signals (tenant, object permissions, reachability)

Key insight: every feature is a human-readable boolean/categorical security property, not a learned embedding.

### 3.5 Hybrid Detection Architecture

#### GATv2-Based Classification (Mathematical Foundation)

GATv2 message-passing equations:

$$\alpha_{ij}^{(l)} = \text{softmax}_j\left(\mathbf{a}^T \text{LeakyReLU}\left(\mathbf{W}[\mathbf{h}_i^{(l)} \| \mathbf{h}_j^{(l)} \| \mathbf{e}_{ij}]\right)\right)$$

$$\mathbf{h}_i^{(l+1)} = \|_{k=1}^{K} \sum_{j \in \mathcal{N}(i)} \alpha_{ij}^{(l,k)} \mathbf{W}^{(k)} \mathbf{h}_j^{(l)}$$

Justify WHY attention matters: the protective relationship between a middleware guard and an endpoint is asymmetric and context-dependent. A role check protects differently depending on which data access it guards.

#### Target-Aware Attention Pooling (Mathematical Foundation)

Key architectural innovation. Standard global pooling loses focus on the specific endpoint being classified:

$$s_i = \mathbf{w}^T \tanh(\mathbf{W}_s [\mathbf{h}_i \| \mathbf{h}_{target}])$$
$$\alpha_i = \text{softmax}(s_i)$$
$$\mathbf{z} = \sum_i \alpha_i \mathbf{h}_i$$
$$\hat{y} = \text{MLP}([\mathbf{z} \| \mathbf{h}_{target}])$$

This ensures the model's attention is anchored to the endpoint being evaluated.

#### Five Structural Rules (Formal Boolean Logic)

- $R_1$: $\exists v \in V : \tau_V(v) = \text{EP} \land \neg\text{auth}(v) \land \text{reaches}(v, \text{DA}) \land \neg\text{public}(v) \Rightarrow \text{MISSING\_AUTH}$
- $R_2$: $\exists v : \text{reaches\_privileged}(v) \land \neg\exists m \in \text{path}(v, DA) : \text{guard}(m) = \text{ROLE} \Rightarrow \text{MISSING\_ROLE}$
- $R_3$: $\exists v : \text{has\_param}(v) \land \exists e : \tau_E(e) = \text{ID\_FLOW} \land \neg\text{ownership\_on\_path}(v, DA) \Rightarrow \text{IDOR}$
- $R_4$: $\exists v : \text{reaches\_tenant\_data}(v) \land \neg\text{tenant\_scoped}(v) \Rightarrow \text{TENANT\_ISO}$
- $R_5$: $\exists v : \text{model\_perm}(v) \land \neg\text{obj\_perm\_on\_path}(v) \Rightarrow \text{OBJ\_PERM\_BYPASS}$

#### Complementarity: Neural + Logical

- Rules: complete for explicitly encodable patterns, guaranteed interpretability
- GNN: captures interaction effects beyond rule expressiveness
- Combined: GNN proposes → validator confirms + explains

### 3.6 Interpretability by Design

The system provides structural interpretability:
- Each Finding traces an explicit path: ENDPOINT → [missing MIDDLEWARE] → DATA_ACCESS
- Explanation derived from graph structure, not learned attention weights
- Contrast with post-hoc tools (GNNExplainer): those learn WHICH subgraph mattered; our validator CONSTRUCTS the explanation from the path

This satisfies RQ2 by design, not by additional tooling.

### 3.7 Conclusion

Summary of theoretical framework. Transition to engineering realization.
