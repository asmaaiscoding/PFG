## §3.1 Introduction

**Content:** Bridge from Part I (state of the art). Position the contribution clearly:

"Existing vulnerability detection systems follow two dominant paradigms:
(1) NLP-based approaches (CodeBERT, VulBERTa, LineVul) that treat source code as token
sequences and detect surface patterns via learned embeddings, and
(2) Graph-based approaches on Code Property Graphs (CPGs) that combine AST, CFG, and PDG
into a single heterogeneous graph, then use GNNExplainer for post-hoc interpretability.

Our approach differs fundamentally: we construct a purpose-built authorization-specific graph
— the Program Flow Graph (PFG) — with interpretable features that directly encode security
properties. This eliminates the need for both opaque embeddings and post-hoc explanation tools.
Unlike CPG-based systems that require GNNExplainer to interpret predictions over thousands of
AST nodes, our PFG provides inherent interpretability: each node represents a concrete
architectural component (endpoint, middleware, service, data access), and each feature encodes
a specific authorization property (has_auth_decorator, has_role_check, performs_ownership_filter).
The structural validator traces explicit paths from endpoint to data access, producing
human-readable explanations without additional interpretation layers."

State what Chapter 3 delivers: formal problem definition, positioning vs SOTA, PFG definition,
GNN architecture, and structural validator design.

## §3.2 Problem Formalization

### §3.2.1 Threat Model and Scope

**Content:**
- Attacker model: authenticated user with valid credentials attempting privilege escalation
  or unauthorized object access (not injection, not XSS)
- Assets: REST API endpoints exposing object-level resources via database queries
- Trust boundaries: Authentication layer → Authorization layer → Data Access layer
- Scope: server-side Django/DRF and Spring Boot applications with REST APIs
- Out of scope: client-side vulns, injection, cryptographic flaws, network-level attacks

**Diagram:** Trust boundary diagram showing HTTP request flow through auth layers to DB.

### §3.2.2 Taxonomy of Authorization Vulnerabilities (5 Subtypes)

**Content:** Formal definition of each targeted vulnerability class:

| Subtype | CWE | Definition |
|---------|-----|------------|
| MISSING_AUTH | CWE-306 | Endpoint reachable without any identity verification before data access |
| MISSING_ROLE | CWE-862 | Endpoint verifies identity but not privilege level for sensitive operations |
| IDOR | CWE-639 | Route parameter flows to data access without ownership verification |
| TENANT_ISOLATION_FAILURE | CWE-284 | Multi-tenant data reachable without tenant scoping predicate |
| OBJECT_LEVEL_PERMISSION_BYPASS | CWE-285 | Object-level permission exists in model but not enforced on access path |

Additional classification labels: SAFE, COMBINED (multiple subtypes), INTENTIONALLY_PUBLIC.

For each subtype: formal definition, minimal code example (Django + Spring), CWE mapping,
OWASP API Security Top-10 2023 mapping.

**Justify scope:** "Standard vulnerable-application benchmarks (OWASP WebGoat, DVWA) are
unsuitable for our work: they target injection vulnerabilities (SQLi, XSS, CSRF) in
single-file educational exercises, not authorization flaws in production REST APIs with
hundreds of endpoints, ViewSets, permission_classes, and layered middleware stacks.
Authorization vulnerabilities are structural — they manifest as the ABSENCE of checks
along execution paths, not as the PRESENCE of exploitable input handling."

### §3.2.3 Research Questions

**Content:** Three research questions in GQM (Goal-Question-Metric) format:

- RQ1 (Detection Effectiveness): Can a domain-specific graph representation of authorization
  flows effectively detect access control vulnerabilities in real-world applications?
  Metric: Precision, Recall, F1 on real CVE benchmark.

- RQ2 (Inherent Interpretability): Does the PFG provide interpretable detection results
  without requiring post-hoc explanation tools (GNNExplainer, SHAP)?
  Metric: Each finding includes endpoint_id + subtype + path-based explanation.

- RQ3 (Comparison with SOTA): How does GNN-based detection compare to rule-based analysis
  and existing SAST tools (Semgrep, CodeQL)?
  Metric: Side-by-side P/R/F1 on same benchmark.

## §3.3 Positioning: Why Not Existing Approaches

### §3.3.1 Limitations of NLP-Based Detection (CodeBERT, VulBERTa)

**Content:**
- These systems treat code as TOKEN SEQUENCES (like natural language)
- CodeBERT produces 768-dim opaque embedding vectors — cannot answer "does this endpoint
  have an authentication check before it queries the database?"
- They detect SURFACE PATTERNS (variable names, API usage similarity) not STRUCTURAL
  PROPERTIES (presence/absence of authorization checks along execution paths)
- Authorization vulnerabilities are NOT lexical — a function can be vulnerable or safe
  depending on what MIDDLEWARE sits between it and the data layer
- 768-dim learned embeddings provide no interpretability: why was this flagged?

### §3.3.2 Limitations of CPG + GNNExplainer

**Content:**
- Code Property Graphs merge AST + CFG + PDG → thousands of nodes per function
- Most nodes are syntactic (assignment, literal, condition) — not security-relevant
- GNNExplainer is needed BECAUSE the graph is opaque (too many irrelevant nodes)
- GNNExplainer learns a mask post-hoc: "which subgraph mattered?" — still indirect
- For authorization: the relevant structure is simple (endpoint → [guards?] → data access)
- A 10,000-node CPG obscures what a 10-node PFG makes obvious

### §3.3.3 Our Design Rationale

**Content:**
- Observation: authorization vulnerabilities are about the STRUCTURE of the request
  processing chain, not about code syntax
- Design choice: model ONLY the authorization-relevant architecture (4 node types)
- Design choice: encode security properties DIRECTLY as features (36-dim, each interpretable)
- Result: no need for CodeBERT (features are hand-crafted and domain-specific)
- Result: no need for GNNExplainer (the graph IS the explanation)
- GNN's role: learn interaction effects and context-dependent patterns that explicit rules
  cannot express (e.g., "this combination of missing checks in this architectural context
  is more likely vulnerable than either alone")

"We made deliberate architectural choices — not 'threw GNN at code.' The PFG is designed
so that its structure directly answers authorization questions, making both opaque embeddings
and post-hoc explanation tools unnecessary."

## §3.4 The Program Flow Graph (PFG)

### §3.4.1 Graph Definition and Schema

**Content:** Formal definition:

G = (V, E, τ_V, τ_E, φ_V, φ_E) where:
- V = set of nodes, τ_V: V → {ENDPOINT, MIDDLEWARE, SERVICE, DATA_ACCESS}
- E ⊆ V × V, τ_E: E → {CALL, IDENTIFIER_FLOW, TENANT_FLOW}
- φ_V: V → ℝ^36 (node feature vector)
- φ_E: E → ℝ^3 (edge feature vector)

Key properties:
- Directed graph (request flows from endpoint toward data access)
- Small (typically 5–50 nodes per application, vs. 1000s for CPG)
- Each node corresponds to a CONCRETE architectural component in source code
- Schema version 1.0 (validated against JSON schema)

**Diagram:** Example PFG for a simple Django ViewSet showing all 4 node types and 3 edge types.

### §3.4.2 Node Types and Attributes

**Content:** Detailed description of each node type:

**ENDPOINT** (HTTP route handler):
- Attributes: http_method, route, route_params[], requires_auth, required_role,
  ownership_check_present, has_route_params, reachable_data_count, has_id_flow,
  unprotected_data_reachable, role_check_present, model_permission_check_present,
  object_permission_check_present, tenant_check_present, has_tenant_scope,
  unscoped_tenant_data_reachable, object_permission_data_reachable

**MIDDLEWARE** (Authorization guard):
- Attributes: guard_type ∈ {AUTHENTICATION, ROLE_CHECK, OWNERSHIP_CHECK, TENANT_CHECK,
  OBJECT_PERMISSION_CHECK}, guard_position (order in chain)

**SERVICE** (Business logic layer):
- Attributes: name (qualname of the function/class)

**DATA_ACCESS** (Database operation):
- Attributes: operation ∈ {READ, WRITE, UPDATE, DELETE}, target_entity,
  has_ownership_predicate, has_tenant_predicate, has_object_permission_check

### §3.4.3 Edge Types and Semantics

**Content:**
- CALL: function invocation (endpoint → service → data_access)
- IDENTIFIER_FLOW: tainted route parameter propagates to a data access argument
  (critical for IDOR detection)
- TENANT_FLOW: tenant/organization scoping propagation

### §3.4.4 Feature Engineering (36-dim Node Vector + 3-dim Edge Vector)

**Content:** Complete feature vector layout:

```
Node features (36 dimensions):
[0:4]   node_type one-hot (ENDPOINT, MIDDLEWARE, SERVICE, DATA_ACCESS)
[4:9]   http_method one-hot (GET, POST, PUT, DELETE, PATCH)
[9]     requires_auth (binary)
[10:15] required_role one-hot (NONE, USER, MODERATOR, ADMIN, SUPERADMIN)
[15]    ownership_check_present (binary)
[16:19] guard_type partial one-hot (3 dims)
[19:23] operation_type one-hot (READ, WRITE, UPDATE, DELETE)
[23]    has_ownership_predicate (binary)
[24]    has_route_params (binary)
[25]    reachable_data_count (normalized float)
[26]    has_id_flow (binary)
[27]    unprotected_data_reachable (binary)
[28]    role_check_present (binary)
[29]    model_permission_check_present (binary)
[30]    object_permission_check_present (binary)
[31]    tenant_check_present (binary)
[32]    has_tenant_scope (binary)
[33]    unscoped_tenant_data_reachable (binary)
[34]    object_permission_data_reachable (binary)
[35]    tenant/object guard signal (0.0 / 0.33 / 0.66 / 1.0)

Edge features (3 dimensions):
[0] CALL
[1] IDENTIFIER_FLOW
[2] TENANT_FLOW
```

**Key argument:** Every single feature is:
(a) directly interpretable by a human ("does this endpoint require auth? yes/no")
(b) directly relevant to authorization decisions
(c) computable without GPU or pre-trained language model

Contrast with CodeBERT: their 768-dim vector encodes "code semantics" generically —
you cannot inspect dimension 42 and say "this means there's no permission check."

### §3.4.5 PFG Construction Pipeline

**Content:** High-level algorithm:
1. Discover endpoints (URL patterns, router registrations, annotated controllers)
2. Annotate authentication/authorization (decorators, mixins, settings, annotations)
3. Build call graph (AST traversal with alias resolution)
4. Detect data access operations (ORM calls, repository methods)
5. Track identifier flows (intra-procedural taint from route params)
6. Assemble PFG (create nodes, connect edges, compute features)
7. Validate against JSON schema

Framework-specific implementations described in Chapter 4 (§4.3).

## §3.5 GNN-Based Vulnerability Detection

### §3.5.1 Why GNN on Top of Rules?

**Content:**
- Rules detect EXPLICIT patterns (if no auth AND data access → vulnerable)
- But real-world authorization is CONTEXTUAL:
  - An endpoint without @login_required might be protected by a class-level mixin
  - A missing ownership check might be acceptable if the endpoint only reads public data
  - The COMBINATION of multiple weak signals may indicate vulnerability
- GNN learns these interaction effects from labeled data
- Rules provide the FLOOR (never miss obvious cases); GNN raises the CEILING

### §3.5.2 PathAnalyzer Architecture (Primary Model)

**Content:** Detailed architecture:

```
Input: PFG as PyG Data object
  - x: [N, 36] node features
  - edge_index: [2, E] edge connectivity
  - edge_attr: [E, 3] edge features
  - target_mask: [N] binary mask indicating the endpoint being classified

Architecture:
  1. Input projection: Linear(36 → 64)
  2. GATv2Conv layers (×3):
     - GATv2Conv(64, 16, heads=4, edge_dim=3, concat=True) → 64-dim output
     - Dropout(0.1)
  3. Target-aware attention pooling:
     - Concatenate each node's embedding with target endpoint embedding → [N, 128]
     - Score network: Linear(128 → 64) + Tanh + Linear(64 → 1)
     - Softmax over scores → attention weights
     - Context = weighted sum of node embeddings
  4. Classification head:
     - Concat(target_embedding, context) → [128]
     - Linear(128 → 64) + ReLU + Dropout(0.1) + Linear(64 → 8)

Output: 8-class logits
  [SAFE, MISSING_AUTH, MISSING_ROLE, IDOR, TENANT_ISOLATION_FAILURE,
   OBJECT_LEVEL_PERMISSION_BYPASS, COMBINED, INTENTIONALLY_PUBLIC]
```

**Justify GATv2 over GCN/GraphSAGE:**
- Attention mechanism captures ASYMMETRIC relationships (an auth middleware protects
  downstream nodes but not upstream ones)
- Multi-head attention (4 heads) captures different aspects of authorization relationships
- Edge features (3-dim) integrated directly into attention computation

**Justify target-aware pooling:**
- Unlike global mean/max pooling, focuses representation on the CONTEXT of the specific
  endpoint being classified
- Different endpoints in the same graph may have different vulnerability status
- The model learns "what context around THIS endpoint matters for classification"

### §3.5.3 PfgAnomalyDetector (Binary Screening Model)

**Content:**
- GINEConv (3 layers), hidden_dim=64
- Global pooling: concat(mean_pool, max_pool) → 128-dim
- MLP: Linear(128→64) + ReLU + Dropout + Linear(64→2)
- Output: binary (vulnerable vs. benign)
- Role: fast initial screening before detailed multi-class analysis

### §3.5.4 Multi-Class Classification (8 Classes)

**Content:**
- Class-weighted CrossEntropyLoss to handle severe imbalance
  (most endpoints are SAFE; vulnerable subtypes are rare)
- Per-subtype confidence thresholds (not uniform 0.5)
- COMBINED class for endpoints with multiple simultaneous vulnerabilities
- INTENTIONALLY_PUBLIC for endpoints explicitly marked as public (AllowAny, @PermitAll)
  — prevents false positives on public API endpoints

## §3.6 Structural Validator (Rule Baseline)

### §3.6.1 Five Detection Rules

**Content:** Formal rule definitions:

**R1 — MISSING_AUTH:**
  Condition: endpoint.requires_auth = False ∧ ∃ path(endpoint →* data_access)
  Exclusion: endpoint.is_intentionally_public = True

**R2 — MISSING_ROLE:**
  Condition: endpoint reaches data_access on privileged entity (admin-only or
  WRITE/DELETE on shared resource) ∧ ¬∃ middleware(ROLE_CHECK) on any path

**R3 — IDOR:**
  Condition: endpoint.has_route_params ∧ ∃ identifier_flow(route_param → data_access)
  ∧ data_access.operation on ownership-bearing entity
  ∧ ¬∃ middleware(OWNERSHIP_CHECK) on path ∧ data_access.has_ownership_predicate = False

**R4 — TENANT_ISOLATION_FAILURE:**
  Condition: tenant-scoped data reachable ∧ ¬endpoint.has_tenant_scope
  ∧ ¬data_access.has_tenant_predicate

**R5 — OBJECT_LEVEL_PERMISSION_BYPASS:**
  Condition: model-level permission evidence exists (object_permission_data_reachable)
  ∧ route-param object access ∧ ¬object_permission_check on path

### §3.6.2 Role as Interpretability Layer

**Content:**
- Each Finding contains: endpoint_id, subtype, data_access_id, human-readable explanation
- Example: "Endpoint 'UserViewSet.retrieve' reaches DataAccess 'User.objects.get(pk=pk)'
  via identifier_flow from route param 'pk' without ownership verification"
- This IS the explanation — no GNNExplainer needed
- The validator answers: WHERE (endpoint), WHAT (subtype), WHY (path trace)

### §3.6.3 Complementarity: Rules + GNN

**Content:**
- Rules: high precision on explicit patterns, but limited to patterns we can formalize
- GNN: learns from data, captures implicit patterns and interaction effects
- Combined architecture:
  - During TRAINING: rules provide weak supervision labels for unlabeled endpoints
  - During INFERENCE: GNN proposes candidates, validator confirms/explains OR
    validator catches what GNN misses (ensemble approach)
- Ablation study (Chapter 5) quantifies the contribution of each component

## §3.7 Conclusion

**Content:** Summary of design choices:
1. Domain-specific graph (PFG) → inherent interpretability
2. Hand-crafted 36-dim features → no opaque embeddings
3. GATv2 with target-aware pooling → context-sensitive classification
4. Structural validator → human-readable explanations without post-hoc tools
5. Rules + GNN complementarity → precision floor with learning ceiling

## §4.3 Framework-Specific Extractors

### §4.3.1 Django Extractor (AST-Based)

**Content:** Six sub-modules that compose the PFG:

**Endpoint Discovery** (`endpoints.py`):
- Parses `urls.py` for `path()`, `re_path()`, `include()`, DRF `DefaultRouter.register()`
- Handles CBV auto-method generation (ViewSet → list/create/retrieve/update/destroy)
- Output: list[DiscoveredEndpoint] with route, http_method, handler_qualname

**Auth Annotation** (`auth.py`):
- Inspects handler AST for decorators: @login_required, @permission_required,
  @staff_member_required, @user_passes_test
- DRF patterns: @api_view + @permission_classes, class-level permission_classes
- Mixins: LoginRequiredMixin, PermissionRequiredMixin, UserPassesTestMixin
- Settings: REST_FRAMEWORK["DEFAULT_PERMISSION_CLASSES"] inheritance
- Output: EndpointAuth (requires_auth, required_role, is_intentionally_public)

**Call Graph** (`callgraph.py`):
- Recursive AST traversal with per-module alias map (import resolution)
- Bounded depth (max_depth=8) to prevent explosion
- Scope: intra-project only (no dynamic dispatch, no runtime decorators)
- Output: set[CallEdge] (src_qualname → dst_qualname)

**Data Access Detection** (`dataaccess.py`):
- Identifies Django ORM calls in function bodies
- Operations: READ (.all, .filter, .get, .count, .values), WRITE (.create, .bulk_create),
  UPDATE (.update, .save), DELETE (.delete)
- Ownership detection:
  - DIRECT: `queryset.filter(user=request.user)`
  - INDIRECT: FK traversal `object__owner=request.user`
  - NONE: no ownership predicate found
- Tenant hints: `tenant`, `tenant_id`, `organization`, `org`, `workspace` parameter names

**Identifier Flow** (`idflow.py`):
- Intra-procedural taint propagation from route parameters
- Algorithm: initialize taint set from function params → walk statements →
  propagate through assignments → emit FlowSink when tainted value reaches a call
- Connects route params to data access arguments (critical for IDOR detection)

**Build Orchestrator** (`build.py`):
- Composes all sub-extractors into final PFG
- Resolves cross-references (endpoint → callgraph → data_access)
- Inserts MIDDLEWARE nodes for detected guards
- Computes derived features (reachable_data_count, unprotected_data_reachable, etc.)

### §4.3.2 Spring Extractor (Regex-Based)

**Content:** Pragmatic single-file extractor for Java/Spring:

**Endpoint Discovery:**
- Class-level: @RestController/@Controller + @RequestMapping base path
- Method-level: @GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping
- JAX-RS: @Path class + @GET/@POST/@PUT/@DELETE methods

**Auth Annotation:**
- @PreAuthorize("hasRole(...)"), @Secured({...}), @RolesAllowed({...})
- @DenyAll (always blocked), @PermitAll (intentionally public)
- Absence of auth annotation + no @PermitAll → requires_auth=False

**Data Access:**
- Repository field detection: fields with type ending in `Repository`/`JpaRepository`
- Method patterns: find* → READ, save* → UPDATE, delete* → DELETE
- Ownership heuristic: method name contains `ByOwner`/`ByUser`/`ByCurrentUser`

**Trade-off:** No full Java AST parsing → cannot resolve all patterns, but covers
80%+ of standard Spring Boot applications with minimal infrastructure.

### §4.4.2 Augmentation by Mutation (5 Strategies)

**Content:**
For each real PFG containing properly-secured endpoints, generate vulnerable variants
by selectively REMOVING authorization guards:

| Strategy | Mutation | Produces |
|----------|----------|----------|
| remove_auth_guard | Strip authentication middleware | MISSING_AUTH sample |
| remove_role_guard | Strip role-check middleware | MISSING_ROLE sample |
| remove_idor_check | Remove ownership predicate from data access | IDOR sample |
| remove_tenant_predicate | Remove tenant scoping from queries | TENANT_ISOLATION sample |
| remove_object_permission | Remove object-level permission check | OBJECT_PERM_BYPASS sample |

Constraints:
- Only augment endpoints with reachable data access (prevents unrealistic samples)
- Cap: 48 augmented samples per manifest (prevents over-representation)
- Metadata tracked: `augmented=True`, `augmentation_strategy=...` for ablation

**Key insight:** This is NOT synthetic data generation from scratch — it's MUTATION of
real application PFGs. The surrounding architecture (other endpoints, services, data access
patterns) remains realistic. Only the specific guard is removed.

### §4.4.3 Weak Supervision (Rule Pseudo-Labels)

**Content:**
- Apply the 5-rule structural validator (§3.6) to UNLABELED endpoints in training manifests
- Generate training samples from high-confidence predictions
- Confidence threshold: 0.35 (conservative — only clear rule matches)
- Excludes: advisory-backed labels (already in ground truth), intentionally-public endpoints
- Cap: 64 pseudo-labeled samples per manifest
- All marked `weak_supervision=True` for ablation tracking

**Motivation:** Real CVE advisories label only the VULNERABLE endpoint — all other
endpoints in the same app are unlabeled (not confirmed safe). Weak supervision recovers
additional signal from rule-based analysis of these unlabeled endpoints.

### §4.4.4 Synthetic Data for Pre-Training

**Content:**
- Generated PFGs with controlled vulnerability patterns using the synthetic generator
- Contrastive pairs: secure variant ↔ vulnerable variant (differ only in guards)
- Used for two-stage training: contrastive pre-training establishes general patterns
  before fine-tuning on real data
- 5000+ synthetic graph pairs covering all 5 subtypes

**Role:** Proof-of-concept validation that the PFG representation CAN distinguish
vulnerable from secure patterns. Once validated, we transitioned to real-world data.

### §4.4.5 Training Split Strategy (No Contamination)

**Content:**
- Leave-one-app-out cross-validation: all CVEs from same application in same split
- `split_manifests_by_group()`: groups by application name
- Ensures NO data leakage: model never sees any endpoint from the test app during training
- Deterministic splits with reproducible seeding
- Standard ratio: 80% train / 10% validation / 10% test

## §4.5 Training Pipeline

### §4.5.1 Progressive Training Strategy

**Content:** Three configurations compared:

**Config A — Real-Only:**
- Training samples directly from 75 CVE manifests
- One labeled sample per endpoint (positive = manifest finding, negative = no finding)
- Baseline: what can the model learn from real data alone?

**Config B — Real + Augmented + Weak Supervision:**
- Real samples + augmented mutations (up to 48/manifest) + pseudo-labels (up to 64/manifest)
- Significantly more training data, especially for rare subtypes
- Tests whether augmentation and weak supervision improve generalization

**Config C — Two-Stage (Synthetic Pre-train → Real Fine-tune):**
- Stage 1: Contrastive pre-training on synthetic PFG pairs
- Stage 2: Fine-tune on real + augmented data
- Tests whether pre-training on synthetic data provides useful initialization

### §4.5.2 Hyperparameters

**Content:**

| Parameter | Value |
|-----------|-------|
| Optimizer | AdamW |
| Loss | Class-weighted CrossEntropyLoss |
| Architecture | GATv2Conv, 3 layers, 4 heads |
| Hidden dimension | 64 |
| Dropout | 0.1 |
| Split | 80/10/10 (train/val/test) |
| Early stopping | On validation loss (patience=10) |
| Class weights | Inverse frequency of each class |
| Seed | Fixed for reproducibility |

### §4.5.3 Ablation Studies

**Content:** Controlled experiments to isolate contributions:

- **GNN vs. MLP baseline:** PathAnalyzer (graph-aware) vs. EndpointMLP (features only, no graph)
  → Quantifies the contribution of graph structure
- **GNN vs. Rules:** PathAnalyzer vs. 5-rule structural validator
  → Quantifies what the model learns beyond explicit rules
- **Feature decontamination:** Remove label-correlated features (indices 9, 15, 23, 27–35)
  → Ensures model doesn't simply memorize feature→label mapping
- **With/without augmentation:** Configs A vs. B
  → Quantifies augmentation contribution
- **With/without pre-training:** Configs B vs. C
  → Quantifies synthetic pre-training contribution

## §5.4 Failure Mode Analysis

### §5.4.1 Where the System Succeeds

**Content:**
- DRF-standard ViewSets with clear permission_classes
- Applications with explicit decorator-based auth
- Standard routing patterns (DefaultRouter, path())
- IDOR where route params flow directly to ORM .get(pk=pk)

### §5.4.2 Where the System Fails

**Content:**
- Non-standard Django patterns (custom middleware stacks, signal-based auth)
- Dynamic dispatch (runtime permission decisions, database-stored permissions)
- Spring applications with complex SecurityFilterChain configurations
- Custom auth backends that don't use standard decorators/annotations
- Applications where authorization is enforced at the database/query level only

### §5.4.3 Error Taxonomy

**Content:** Classify errors into:
- **Extractor limitations:** auth pattern not recognized → incorrect PFG → wrong prediction
  (fixable by extending extractors)
- **Model limitations:** correct PFG but wrong classification
  (requires more training data or architectural changes)
- **Scope limitations:** vulnerability type not modeled
  (requires extending the taxonomy)

## §5.5 Discussion

### §5.5.1 Interpretability Without Post-Hoc Tools (RQ2)

**Content:**
"Our PFG provides inherent interpretability that CPG-based systems with GNNExplainer cannot
match. When PathAnalyzer classifies an endpoint as IDOR, the structural validator immediately
provides: 'Endpoint UserViewSet.retrieve reaches DataAccess User.objects.get(pk=pk) via
identifier_flow from route param pk without ownership verification on the path.'

This explanation maps directly to actionable information for a developer:
- WHERE: the specific endpoint and route
- WHAT: the vulnerability type (IDOR)
- WHY: the missing check (no ownership verification)
- HOW TO FIX: add ownership filtering (queryset.filter(owner=request.user))

GNNExplainer, by contrast, would output: 'these 5 nodes in the graph were most important
for the prediction' — requiring additional interpretation to translate into actionable advice.
Our approach eliminates this interpretation gap by design."

### §5.5.2 The Performance Gap: Extractor Coverage (Honest Analysis)

**Content:**
- The gap between DRF-standard (F1=0.727) and full benchmark (F1=0.068) is primarily
  due to EXTRACTOR COVERAGE, not model capability
- When the extractor accurately models the application → model performs well
- When the extractor misses patterns → PFG is incorrect → model has wrong input
- This is NOT a fundamental limitation of the approach — it's an engineering challenge
  (extend extractors to cover more patterns)
- Compare: even Semgrep/CodeQL require rules for each pattern they detect

### §5.5.3 Scalability and Practical Applicability

**Content:**
- PFG construction: O(endpoints × call_depth) — linear in application size
- GNN inference: milliseconds per endpoint (36-dim features, small graphs)
- Full analysis of a typical Django app (50–200 endpoints): < 30 seconds
- Practical for CI/CD integration (analyze on every PR)

### §5.5.4 Threats to Validity

**Content:**
- Internal: ground truth from CVE advisories (may miss vulnerabilities not yet discovered)
- External: evaluated on Django/Spring only (generalization to other frameworks unknown)
- Construct: subtype taxonomy may not cover all authorization vulnerability patterns
- Reproducibility: all code, data, and manifests available; deterministic splits
